# Проект: агент-диспетчер по возвратам

## Легенда и цель

«Клевер Маркет» обрабатывает 16 незакрытых обращений RC-6001—RC-6016. Приложение связывает письмо с заказом, проверяет историю и политику, формирует структурированную рекомендацию и два раздельных черновика. Это учебный контур: он не отправляет сообщения, не взаимодействует с внешней системой заказов и не выполняет финансовые операции.

## Роли

- **Агент** читает только письмо, связанный заказ, историю и два документа политики. Он подготавливает факты, маршрут и черновики.
- **Менеджер** видит рекомендацию, основания и историю; подтверждает маршрут или выбирает разрешённое альтернативное действие.
- **Клиентский контур** показывает письмо, товар, состояние обращения и клиентский черновик. До решения менеджера он не получает менеджерскую рекомендацию.

Переключатель ролей в интерфейсе учебный, не является аутентификацией. Серверные API всё равно проверяют роль для каждого чувствительного действия.

## Входные данные и ограничения

- `data/open-cases.json`: неизменяемая очередь из 16 обращений.
- `data/orders.json`: неизменяемый контекст заказов.
- `data/return-history.json`: неизменяемая история четырёх закрытых дел.
- `policy/return-policy.md`, `policy/category-rules.md`: неизменяемые правила.
- SQLite в `data/runtime/returns.sqlite3`: импортированные копии источников, состояния, анализ, учебные разрешения и журнал.
- При наличии `OPENAI_API_KEY` AI API получает текст письма, минимум контекста заказа и применяемые выдержки политики. Ключ остаётся только в переменной окружения. Без ключа работает воспроизводимый серверный анализ.

Модель не изменяет заказ или очередь, не пишет напрямую в базу, не меняет статус, не создаёт разрешение и не отправляет сообщение. Сервер вычисляет допустимый маршрут, проверяет переход и право менеджера. Внешние действия недоступны.

## Пять маршрутов

1. `RECOMMEND_APPROVE` — пригодные факты и нормы показаны менеджеру; разрешение создаётся только после его подтверждения.
2. `RECOMMEND_DENY` — видны установленные факты и конкретная норма отказа; до решения менеджера клиенту не раскрывается рекомендация.
3. `NEED_MORE_INFORMATION` — клиентский черновик содержит только вопросы о неизвестных фактах; известное не спрашивается повторно.
4. `MANUAL_REVIEW` — менеджеру показаны причина передачи, неопределённость, факты и политика; клиенту не обещается исход.
5. `DUPLICATE_OR_PROCESSED` — менеджер видит найденную историю; повторное разрешение блокируется.

## Состояния и финальные условия

- `OPEN` → `WAITING_MANAGER`: только серверный анализ после проверки заказа, истории и политик.
- `WAITING_MANAGER` → `RETURN_AUTHORIZED`: только менеджер подтверждает серверный маршрут `RECOMMEND_APPROVE`; одновременно создаётся одна запись разрешения.
- `WAITING_MANAGER` → `DENIED`, `WAITING_FOR_CUSTOMER`, `MANUAL_REVIEW` или `DUPLICATE_PROCESSED`: только допустимое действие менеджера.
- Любой повторный или неразрешённый переход отклоняется сервером.

Подтверждение других маршрутов не создаёт разрешения. Разрешение уникально для дела и не может появиться из предложения модели.

## Критерии готовности

- Все 16 источников импортируются без изменения исходных файлов и отображаются в очереди.
- Каждое обращение можно разобрать с выводом заказа, истории, фактов, правил, маршрута, недостающих данных и причины остановки.
- Клиентский API не раскрывает рекомендацию и менеджерские материалы до решения.
- Маршрут, переход, права роли и создание разрешения проверяются сервером.
- Журнал фиксирует дело, источники, маршрут, переход и решение менеджера, но не содержит API-ключа.
- Приложение запускается локально; при отсутствии API-ключа действует детерминированный режим.
