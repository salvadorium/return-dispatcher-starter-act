# Спецификация агента-диспетчера

## Контекст и источники

Для выбранного дела сервер загружает письмо из `open-cases.json`, заказ по точному номеру из `orders.json`, историю по номеру заказа из `return-history.json` и оба файла политики. В анализе каждый вывод сопровождается источником, релевантные пункты политики перечисляются по идентификаторам P-1—P-6 и C-1—C-6. Тексты источников не редактируются.

SQLite хранит локальные копии импортированных источников, статус дела, структурированный анализ, менеджерское решение, учебное разрешение и аудит. Импорт идемпотентен (`INSERT OR IGNORE`), поэтому перезапуск не сбрасывает рабочее состояние.

## Возможности модели и границы доверия

Без `OPENAI_API_KEY` действует детерминированный анализатор правил. С ключом сервер отправляет минимальный контекст AI API через OpenAI-compatible Chat Completions: текст письма, имя товара и категорию, рассчитанный сервером маршрут/основание, вопросы и политики. Внешний провайдер может получить текст письма, поэтому режим включается только явной настройкой окружения.

Модель возвращает строго ограниченный JSON: один из пяти маршрутов-кандидатов и два черновика. Сервер проверяет схему и перечисление маршрутов, сохраняет совпадение/расхождение с серверным маршрутом, но никогда не принимает маршрут модели за итоговый. Тексты модели доступны только менеджеру как предложения; клиент получает серверный нейтральный черновик или вопросы, сгенерированные из проверенного списка недостающих фактов. Ошибка провайдера возвращается явно и не создаёт неполный анализ.

Модели недоступны SQL, инструменты изменения состояния, заказные/финансовые интеграции и отправка сообщений. Сервер не включает секреты в промпт и не пишет API-ключи в журнал. Письмо трактуется как недоверенные данные, а не инструкция агенту.

## Структурированный анализ

Запись анализа включает `route`, `reason`, `stop_reason`, `facts[]` (метка, значение, источник), `missing_information[]`, `policy_refs[]`, `history[]`, `client_draft`, `manager_draft`, необязательные `model_suggestion` и `model_drafts`. Перед выбором маршрута проверяются полнота фактов, категория, срок и история. При повторе по тому же основанию история имеет приоритет; информационный контакт по другой причине не блокирует новое дело. Для кухонной техники сначала запрашиваются отсутствующие обязательные факты C-5; только после проверки полноты повреждение может потребовать передачи менеджеру по P-6.

Для `NEED_MORE_INFORMATION` вопросы строятся только по отсутствующим обязательным сведениям. Для остальных маршрутов клиент получает нейтральное подтверждение получения без обещания решения. Менеджер получает конкретное основание, историю и ссылки на правила.

## Маршруты: наблюдаемое поведение

| Маршрут | Поведение интерфейса и сервера |
|---|---|
| `RECOMMEND_APPROVE` | Менеджер видит факты и основания. Переход к `RETURN_AUTHORIZED` доступен только после менеджерского подтверждения; тогда создаётся уникальное учебное разрешение. |
| `RECOMMEND_DENY` | Менеджеру показаны обстоятельства и точное основание политики. До решения менеджера клиент видит только нейтральный черновик. |
| `NEED_MORE_INFORMATION` | В клиентском черновике только недостающие вопросы; известные факты повторно не спрашиваются. Черновик не отправляется автоматически. |
| `MANUAL_REVIEW` | Менеджер видит причину передачи, неопределённость, факты и историю. Клиенту не обещают возврат, отказ или срок внешнего действия. |
| `DUPLICATE_OR_PROCESSED` | История и предыдущее разрешение видны менеджеру; сервер не создаёт второе разрешение. |

## Состояния и акторы

- `OPEN`: ожидает анализа; анализ разрешён только в менеджерском API.
- `WAITING_MANAGER`: содержит рекомендацию, но не финальное решение.
- `RETURN_AUTHORIZED`, `DENIED`, `WAITING_FOR_CUSTOMER`, `MANUAL_REVIEW`, `DUPLICATE_PROCESSED`: финалы менеджерского действия (ожидание клиента и ручная проверка остаются рабочими очередями).

Клиент может читать письмо, сведения о заказе, состояние и свой черновик. Менеджер может запустить анализ и зафиксировать одно из действий: подтвердить рекомендацию, изменить на отказ, запросить сведения, передать на ручную проверку, отметить повторным при наличии записи истории. API повторно проверяет роль, текущее состояние, действие и предусловия. Ни клиент, ни модель не могут вызвать менеджерское действие.

Подтверждение рекомендации маршрутизируется сервером. В частности, если серверная рекомендация не `RECOMMEND_APPROVE`, подтверждение не может создать разрешение. Второе решение для дела блокируется.

## Журналирование и проверка

Аудит фиксирует ID дела, событие, список использованных файлов, маршрут, ссылки на правила, старое/новое состояние, действие менеджера и факт создания разрешения. Он не включает ключи, HTTP-заголовки авторизации или полный промпт модели. Отдельный API журнала менеджерский.

Проверки включают API тесты на все 16 исходов, изоляцию контуров, блокирование переходов и уникальность разрешений. Модельный ответ — недоверенный ввод: сервер допускает только известные маршруты и строковые черновики, обрезает размер текста и не использует модельный маршрут для переходов.
